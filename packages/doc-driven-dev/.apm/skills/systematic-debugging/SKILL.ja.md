# 体系的デバッグ（Systematic Debugging）

## 概要

場当たり的な修正は時間を無駄にし、新たなバグを生む。

**核心原則:** 修正を試みる前に必ず根本原因を特定する。症状の修正は失敗である。

## 鉄則

```
根本原因調査なしの修正は禁止
```

## 使用タイミング

あらゆる技術的問題に使用: テスト失敗、本番バグ、予期せぬ動作、パフォーマンス問題、ビルド失敗、統合問題

**特に以下の場合:**
- 時間的プレッシャー下（緊急時は推測が魅力的になる）
- 「一つのクイックフィックス」が明らかに見える時
- 既に複数の修正を試した後
- 前の修正が効かなかった時

## 4つのフェーズ

### Phase 1: 根本原因調査

修正を試みる前に:
1. エラーメッセージを注意深く読む
2. 一貫した再現を確認する
3. 最近の変更を確認する
4. 複数コンポーネントシステムでは診断計装を追加する
5. データフローをトレースする

### Phase 2: パターン分析

1. 動作している類似例を見つける
2. リファレンス実装と比較する
3. 差異を特定する
4. 依存関係を理解する

### Phase 3: 仮説とテスト

1. 単一の仮説を立てる（「X が根本原因だと考える。なぜなら Y」）
2. 最小限の変更でテストする
3. 検証してから進む
4. 分からない時は正直に言う

### Phase 4: 実装

1. 失敗するテストケースを作成する（`test-driven-development` スキルを使用）
2. 単一の修正を実装する（根本原因に対処）
3. 修正を検証する
4. 効かなければ: 3回以上失敗したらアーキテクチャを疑問視する

## レッドフラグ — 中止してプロセスに従う

- 「とりあえずクイックフィックス」
- 「X を変えて動くか見よう」
- 「複数の変更を一度に」
- 「テストはスキップ、手動で確認」
- 「たぶん X だろう」
- 「完全には理解していないがこれで動くかも」
- もう1回修正を試みる（既に2回以上失敗後）

**全てが意味するもの: 中止。Phase 1 に戻る。**
