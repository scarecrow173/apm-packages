# Deep Dive

このスキルは、後続の文書化や実装に必要な論点がまだ曖昧なときに使います。
目的は、選択肢を広げることでも文書を直接書くことでもありません。ユーザーが
本当に欲しい outcome、支配的な制約、判断軸を明らかにすることです。

## 使いどころ

次のようなときに使います。

- リクエストは一般的だが、実務上必要な具体性がない
- ユーザーがどのトレードオフを重視するか明示していない
- 成功条件が曖昧
- 制約、スコープ境界、対象ユーザーを推測で埋めそうになっている
- リポジトリの文脈が質問内容を変えるはずである

次のことには使いません。

- 単純で機械的な変更
- 純粋な情報提供
- spec / ADR / plan を直接書くこと
- 複数案の発散的な ideation

## 基本ルール

1. リポジトリ証拠で答えられることは、先にコードベースを調べる
2. 質問は一度に 1 つだけ行う
3. すべての live question に次を含める
   - `Q:` 質問
   - `GUESS:` 現時点の仮説
   - `RECOMMENDED:` 今この場で自分が勧める答えと理由
4. アンケートをまとめて投げず、判断木を 1 分岐ずつ進める
5. ユーザーが具体的な intent を確認できたら止める

## 進め方

### Step 1: 先にコードベースを調べる

質問前に、面談内容を左右するリポジトリ証拠を集めます。

- 関連ドキュメント、設定、コードパスを読む
- 既存制約や既存パターンを確認する
- すでにリポジトリで確認できる事実を、ユーザーに言い直させない

探索で答えられる質問は、先に探索で片付けます。

### Step 2: 仮説を明示する

現時点の最善の読みと確信度を書きます。

```text
HYPOTHESIS: You want ...
CONFIDENCE: ~40% - missing: ...
```

確信度が 70% 未満なら、足りない情報を短く添えます。

### Step 3: 一問ずつ質問する

各質問は次の形式にします。

```text
Q: ...
GUESS: ...
RECOMMENDED: ...
```

ルール:

- 回答を受ける前に次の質問へ進まない
- 次の分岐を解くのに最短の質問を優先する
- 仮説を隠さず、都度前に出す

### Step 4: 判断木をたどる

追質問で次を絞ります。

- desired outcome
- target user
- why now
- success criteria
- binding constraints
- decision axes
- out-of-scope items

次に聞く 3 問への反応を高い確度で予測できるようになるまで続けます。

### Step 5: 確認済み intent を要約する

最後に簡潔な要約を返します。

```text
Here's what I now think you want:

- Outcome:
- User:
- Why now:
- Success:
- Constraint:
- Decision axes:
- Out of scope:

Yes / no / refine?
```

この確認済み要約が、このスキルの出力です。

## 対話スタイル

- 直接的に進める
- 一度に 1 問だけ聞く
- 避けられる質問より先にリポジトリ証拠を優先する
- ただ尋ねるのではなく、毎回推奨回答を添える
- ユーザーが明示的にモードを変えない限り、解決案の発散には広げない

## Handoffs

確認済み要約のあと:

- 要件を文書化できる状態なら `spec-doc` に渡す
- 具体的な技術判断を ADR に落とせる状態なら `adr-doc` に渡す
- まだ解決案の exploration が必要なら、その目的に合う別スキルへ渡す

## Verification

このスキル適用後に確認すること:

- [ ] 避けられる質問の前にリポジトリ証拠を確認した
- [ ] 最初のターンで仮説と確信度を明示した
- [ ] すべての live question に `Q` / `GUESS` / `RECOMMENDED` がある
- [ ] 質問を一度に 1 つずつ行った
- [ ] 最終出力が outcome / user / why now / success / constraint /
      decision axes / out of scope を含む確認済み要約になっている
