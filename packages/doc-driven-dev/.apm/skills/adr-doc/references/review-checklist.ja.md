# ADR エージェント対応チェックリスト

ADR を確定する前にこのチェックリストを使います。

中核となる問いは、コーディングエージェントがこの ADR を読み、確認質問なしで
判断を実装できるかです。

## 背景

- 何が変わった、壊れた、または判断しないと壊れるのかが説明されている。
- 必要なドメイン用語、略語、システム、制約が明示されている。
- 関連する issue、PR、ADR、ファイル、既存パターンが分かる場合はリンクされている。

## 判断

- 判断が実行可能な具体性を持っている。
- 対象範囲と対象外が明確である。
- 制約が可能な限り測定可能である。
- 不採用の代替案について、なぜ選ばなかったかが説明されている。

## 実装計画

- 影響するファイル、ディレクトリ、モジュール、インターフェイスが示されている。
- 追加、削除、回避する依存関係が示されている。
- 従うべきパターンが、可能な場合は既存コードと結び付いている。
- 避けるべきパターンが明示されている。
- 必要な設定、移行、データ、互換性対応が示されている。

## 検証

- 検証基準がチェックボックスで書かれている。
- 各基準がコマンド、テスト、レビュー手順、観測可能な振る舞いで確認できる。
- 機能面とアーキテクチャ適合性の両方を検証している。
- 「うまく動く」「性能がよい」のような曖昧な表現が、測定可能な確認に置き換えられている。

## よくある不足

| 不足 | 修正 |
| --- | --- |
| 実装計画が「コードを更新する」だけ | ファイル、モジュール、インターフェイス、パターンを示す。 |
| 検証が「動くこと」だけ | コマンド、テスト、指標、レビュー観点を示す。 |
| 選択肢が 1 つだけ | 実質的な代替案、または代替案を退けた理由を記録する。 |
| 背景が暗黙知に依存している | システム、きっかけ、制約、リンクを明示する。 |
| 影響が良い点だけ | リスク、コスト、移行作業、フォローアップタスクを追加する。 |
