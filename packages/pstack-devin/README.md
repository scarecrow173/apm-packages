# pstack-devin

Devin CLI compatible distribution of the upstream
[pstack](https://github.com/cursor/plugins) workflow pack
(`harness/pstack/claude-code`), pinned to a fixed upstream commit.

> Status: the deterministic builder, the generated `devin-plugin/` tree —
> including the Devin runtime adapter overlay — and the first `.apm/`
> primitive (`skills/setup-pstack-devin/`) are committed. Further APM
> primitives land in later issues; see the issue chain under
> [the parent issue](https://github.com/scarecrow173/apm-packages/issues/211).

## Artifacts and boundaries

This directory hosts two related but distinct artifacts:

| Artifact | Location | Consumed by | Contents |
| --- | --- | --- | --- |
| APM package | `packages/pstack-devin/` | `apm install` consumers | Adapter/setup primitives under `.apm/` (ships `skills/setup-pstack-devin/`; more in later issues) |
| Devin plugin | `packages/pstack-devin/devin-plugin/` | `devin plugins install` | Byte-pinned upstream pstack tree plus a thin Devin overlay (generated by `scripts/pstack-devin`; committed) |

`targets:` in `apm.yml` selects which AI runtimes receive this package's APM
primitives. It does **not** imply Devin CLI support: Devin consumes the built
`devin-plugin/` directory, which is produced and distributed separately.

## Upstream pin

`upstream.yml` is the single authority for the upstream repository, path,
and commit. `apm.yml` carries the same pin as a `devDependencies` entry so
that `apm.lock.yaml` attests `resolved_commit` and `content_hash`; the three
values must always agree. A mismatch is a hard failure, not a warning.

Upstream files ship byte-identical except for an explicit overwrite
allowlist. See `docs/upstream-source-decision.md` for the verified
rationale and `docs/verification-apm-0.33.0.md` for the reproduction log.

## Devin runtime adapter

The generated plugin ships `docs/harness/devin.md`, the adapter of record
on Devin: it maps the Cursor tool and `Task`-field names that upstream
skills use (`Task` → `run_subagent`, `AskQuestion` → `ask_user_question`,
`subagent_type` → `profile`, …) onto Devin's runtime, and it wins over the
upstream `docs/harness/claude-code.md` adapter wherever the two disagree.
The always-on root `AGENTS.md` points at it, but pstack stays opt-in —
nothing activates unless the user invokes a pstack skill or `/pstack:<name>`
command.

Overlay policy, enforced by `overlay.yml` and recorded in
`provenance.json`:

- `agents/poteto-agent.md` is a Devin-native overwrite (allowlisted):
  upstream's `is_background` frontmatter and `generalPurpose`/`~/.cursor`
  references live in a machine-parsed profile that instruction-level
  adaptation cannot fix. `agents/comment-sicko.md` stays byte-identical —
  pure persona prose, already valid Devin.
- External skill deps `deslop`, `control-cli`, and `control-ui` ship in
  `cursor-team-kit`, which carries only a `.cursor-plugin/` manifest and
  is not installable as a Devin plugin. APM consumers get the real
  skills transitively — `apm.yml` declares them as virtual `claude_skill`
  dependencies pinned to the same upstream commit, deployed to target
  skill dirs (`.agents/skills/` included, which Devin reads). The
  `devin plugins install` route cannot express dependencies, so plugin
  consumers still get the adapter's plain-words fallback; see
  `docs/devin-adapter-decisions.md`.

The mapping contract is machine-checked: the `audit:compat` script scans
the generated tree and fails on any unclassified harness-API reference,
so a new upstream Cursor API surfaces as an audit error instead of silent
breakage.

```bash
mise exec -- pnpm --dir scripts/pstack-devin run audit:compat
```

## Model setup: `/pstack:setup-pstack`

Upstream's `setup-pstack` skill ships as a thin delegation overwrite: on
Devin, `/pstack:setup-pstack` reads `skills/setup-pstack-devin/SKILL.md`
and follows it. The skill detects models via `devin models list`, asks for
a reasoning budget, and generates:

- `~/.devin/rules/pstack-models.md` — an always-on rule
  (`trigger: always_on`) carrying one `role: slug[, slug…]` line per
  configured role.
- `~/.config/devin/agents/pstack-<slug>.md` and `pstack-<slug>-ro.md` —
  model-pinned custom subagent profiles (write and read-only-intent
  variants) for every slug the rule names. On Windows the agents dir is
  `%APPDATA%\devin\agents\`.

All arithmetic and file emission run through `scripts/setup.mjs`, a
dependency-free Node helper inside the skill
(`node scripts/setup.mjs parse|plan|apply`). Generated files carry a
`# pstack-generated:` sha256 marker, so re-runs are byte-stable and user
edits surface as diffs that need explicit confirmation; obsolete
`pstack-*.md` profiles are deleted only via `--remove` after the
candidates are listed.

The rule and the profiles load at session start — a setup applies to
**new** sessions; the current one keeps its models. Cloud sessions cannot
load plugin profiles: `pstack-*` profiles are local-only.

The same skill ships to APM consumers byte-for-byte at
`.apm/skills/setup-pstack-devin/`; the `apm-sync` test keeps the copy
identical to the overlay source.

## Regenerating `devin-plugin/`

The plugin tree is generated output committed to git. Regenerate and
verify it from the repository root:

```bash
mise exec -- pnpm --dir scripts/pstack-devin run build            # rebuild devin-plugin/
mise exec -- pnpm --dir scripts/pstack-devin run check-generated  # committed tree == fresh rebuild?
```

`check-generated` rebuilds into a scratch directory and compares every
file byte-for-byte; it fails on any drift. See
`docs/build-verification.md` for the recorded evidence.

## Verification

A deterministic, free, local check suite guards the shipped tree. Run
the whole thing from the repository root:

```bash
mise exec -- pnpm --dir scripts/pstack-devin run verify   # L1 + L2 + L3 + unit tests
```

| Command | What it proves |
| --- | --- |
| `run verify:l1` | Build integrity & distribution safety — the committed `devin-plugin/` is a byte-exact rebuild of the pinned upstream + overlay, and the tree carries no secret-shaped tokens, oversized files, or exec-bit/manifest drift |
| `run verify:l2` | Upstream compatibility & references — every harness-API token is a registered vocabulary entry, every shipped doc reference resolves to a real target, and consumer role labels ⊆ `roles.json` keys |
| `run verify:l3` | Distribution shape — `.devin-plugin/plugin.json` schema, `devin-plugin/` layout, `.apm/` and `devin-plugin/` never conflate, and `apm pack`/`apm compile` keep their recorded behavior |
| `run probe:consumer` | **Manual only** — a scratch consumer installs the package via the real `apm` (the `--ref` git form needs network); evidence is appended to `docs/l3-verification.md` |

The per-check guarantee matrix lives in `docs/verification-matrix.md`.
These are static checks: they prove the shipped tree is consistent and
correctly shaped for install — they do **not** prove agent runtime
quality. Real Devin CLI session evidence lives in
`docs/runtime-verification.md` (`#218`): per-skill probes and verdicts,
plus the compatibility/support matrix in its `## 5. Compatibility`
section.

## Layout

```text
packages/pstack-devin/
  apm.yml            # manifest; lists 3 cursor-team-kit skill deps, never the upstream tree
  upstream.yml       # pinned upstream coordinates (single authority)
  apm.lock.yaml      # generated by `apm install`; committed as attestation
  docs/              # verification log and design record (maintainer-facing)
  overlay/           # authored Devin overlay source applied on top of upstream
  overlay.yml        # overwrite allowlist for the overlay (authority)
  devin-plugin/      # generated Devin plugin output (committed; never edit by hand)
  .apm/              # APM primitives (skills/setup-pstack-devin/ ships; more later)
```

## Quickstart

1. Install the Devin plugin (both install paths are under
   [Install](#install)):

   ```bash
   devin plugins install scarecrow173/apm-packages#packages/pstack-devin/devin-plugin
   ```

2. Start a **new** `devin` session — plugin skills, `pstack:*` agent
   profiles, and generated rules load at session start. Every recorded
   probe ran in a session begun after the install and resolved
   `/pstack:*`; whether a running session picks up an install is not
   verified (`docs/runtime-verification.md`, `docs/migration.md` §5).
3. Invoke `/pstack:poteto-help`. Verified on `devin 3000.12.57`
   (Windows): the skill resolves, its body loads, and it routes to the
   right pstack file (`docs/runtime-verification.md` §2).

Further reading:

- `docs/runtime-verification.md` — per-skill real-CLI evidence and the
  compatibility/support matrix.
- `docs/migration.md` — switching between upstream `pstack` and this
  distribution: name collision, backup, rollback, config locations.
- `docs/verification-matrix.md` — what each deterministic `verify:*`
  check proves.
- `docs/distribution-verification.md` — install/remove evidence for
  both plugin paths and the APM path.

## Install

Two install paths serve the two artifacts — pick per goal:

| Path | Command | What you get |
| --- | --- | --- |
| Devin plugin | `devin plugins install scarecrow173/apm-packages#packages/pstack-devin/devin-plugin` | Full pstack on Devin CLI — every `/pstack:*` skill, the `pstack:poteto-agent`/`pstack:comment-sicko` agents, and the always-on `AGENTS.md` rule |
| APM package | `apm install pstack-devin@apm-packages` (after `apm marketplace add scarecrow173/apm-packages`) | Only this package's `.apm/` primitives — today the single `setup-pstack-devin` skill |

`apm install` deploys APM primitives only; it cannot install or activate
the Devin plugin. For a local checkout, pass the plugin directory
directly — `--local` scopes the install to this machine:

```bash
devin plugins install /path/to/apm-packages/packages/pstack-devin/devin-plugin --local
```

Remove with `devin plugins remove pstack` (add `--local` for `--local`
installs). Upstream `cursor/plugins` also ships a plugin named `pstack`,
and only one can be installed at a time — `devin plugins info pstack`
disambiguates: this distribution reports `version:` `0.1.0` and a
`source:` under `scarecrow173/apm-packages`. Verified install evidence
lives in `docs/distribution-verification.md`; switching between the two
`pstack` plugins is covered by `docs/migration.md`.
