# 漸進的実装（Incremental Implementation）

## 概要

薄い垂直スライスで構築する — 一つの部品を実装し、テストし、検証してから拡張する。一度に機能全体を実装しない。各インクリメントはシステムを動作可能・テスト可能な状態に保つ。これが大規模機能を管理可能にする実行規律である。

## 使用タイミング

- 複数ファイルにまたがる変更の実装時
- タスク分解から新機能を構築する時
- 既存コードのリファクタリング時
- テスト前に 100 行以上書こうとしている時

**使用しない場合:** スコープが既に最小限の単一ファイル・単一関数の変更。

## インクリメントサイクル

```
┌──────────────────────────────────────┐
│                                      │
│   実装 ──→ テスト ──→ 検証 ──┐       │
│    ▲                         │       │
│    └───── コミット ◄─────────┘       │
│            │                         │
│            ▼                         │
│        次のスライス                   │
│                                      │
└──────────────────────────────────────┘
```

各スライスで:

1. **実装** — 最小の完全な機能片を実装
2. **テスト** — テストスイートを実行
3. **検証** — スライスが期待通り動作することを確認
4. **コミット** — 説明的なメッセージで保存
5. **次のスライスへ** — 前進する、再開しない

## スライス戦略

### 垂直スライス（推奨）

スタックを通る完全なパスを一つずつ構築する。各スライスはエンドツーエンドで動作する機能を提供する。

### コントラクトファースト

バックエンドとフロントエンドの並行開発時: API コントラクトを先に定義し、各側を独立実装してから統合する。

### リスクファースト

最もリスクの高い・不確実な部分を最初に取り組む。早期に失敗を発見する。

## 実装ルール

### Rule 0: シンプルさ優先

コードを書く前に「動く最もシンプルなものは何か？」と問う。明らかに正しいナイーブな版を先に実装する。

### Rule 0.5: スコープ規律

タスクが要求するものだけに触れる。スコープ外の改善に気づいたら、修正せずメモする。

### Rule 1: 一度に一つ

各インクリメントは一つの論理的な変更のみ。

### Rule 2: コンパイル可能に保つ

各インクリメント後、プロジェクトがビルドでき既存テストが通ること。

### Rule 3: 未完成機能にはフィーチャーフラグ

### Rule 4: 安全なデフォルト

### Rule 5: ロールバック可能

各インクリメントが独立して revert 可能であること。

## 検証チェックリスト

- [ ] 各インクリメントが個別にテスト・コミットされた
- [ ] 全テストスイートが通る
- [ ] ビルドがクリーン
- [ ] 機能が仕様通りエンドツーエンドで動作する
- [ ] コミットされていない変更が残っていない
