# 疑念駆動開発（Doubt-Driven Development）

## 概要

自信のある回答は正しい回答ではない。長いセッションはコンテキストを蓄積し、仮定を静かに「事実」に変える。疑念駆動開発は、非自明な出力が確定する前に、**否定**に偏ったフレッシュコンテキストのレビュアーを具現化する規律である。

## 使用タイミング

判断が**非自明**である条件（いずれか一つ以上）:

- 分岐ロジックを導入・変更する
- モジュールまたはサービス境界を越える
- 型システムが検証できない性質を主張する（スレッドセーフティ、冪等性、順序、不変条件）
- 正確性が将来の読者には見えないコンテキストに依存する
- 影響範囲が不可逆（本番デプロイ、データ移行、パブリック API 変更）

**使用しない場合:**

- 機械的操作（リネーム、フォーマット、ファイル移動）
- 明確で曖昧さのないユーザー指示への対応
- 既存コードの読み取り・要約
- 明らかに正しい一行変更
- ユーザーが速度を検証より優先した場合

## プロセス

```
Doubt cycle:
- [ ] Step 1: CLAIM — 主張 + なぜ重要かを記述
- [ ] Step 2: EXTRACT — アーティファクト + 契約を分離、推論を除去
- [ ] Step 3: DOUBT — 敵対的プロンプトでフレッシュコンテキストレビュアーを呼び出す
- [ ] Step 4: RECONCILE — 各指摘をアーティファクトテキストに照らして分類
- [ ] Step 5: STOP — 停止条件を満たす（些末な指摘のみ、3サイクル、またはユーザーオーバーライド）
```

### Step 1: CLAIM — 確定させるものを表面化

### Step 2: EXTRACT — 最小レビュー可能単位

レビュアーには**アーティファクト**と**契約**のみ渡す。推論は除去する。

### Step 3: DOUBT — フレッシュコンテキストレビュアーを呼び出す

レビュアーへのプロンプトは**敵対的**でなければならない。「問題を見つけよ」であり「これは良いか？」ではない。

**ARTIFACT + CONTRACT のみ渡す。CLAIM は渡さない。**

#### クロスモデルエスカレーション

インタラクティブセッション: 常にクロスモデルを提案する。ユーザーが判断する。
非インタラクティブ: スキップし、スキップを明示する。

### Step 4: RECONCILE — 指摘を統合

各指摘を優先順で分類:
1. **契約誤読** — 契約を修正して再分類
2. **有効 + 対処可能** — 実際の問題。アーティファクトを変更してループ
3. **有効なトレードオフ** — 実際だが受容可能なコスト。明示的に文書化
4. **ノイズ** — レビュアーが持たないコンテキスト下では正しい

### Step 5: STOP — 有限ループ

停止条件: 些末な指摘のみ / 3サイクル完了 / ユーザーの "ship it"

## 他スキルとの関係

- **requesting-code-review**: 補完的。コードレビューは事後判定、疑念駆動は判断中のインライン検証
- **source-driven-development**: SDD はフレームワーク事実を検証、疑念駆動はアーティファクトに関する推論を検証
- **test-driven-development**: TDD の RED ステップは具体化された疑念 — 失敗テストは反証の試み
- **systematic-debugging**: レビュアーが実際の障害モードを指摘したら、デバッグスキルに移行

## 検証チェックリスト

- [ ] 非自明な判断はすべて CLAIM として明示した
- [ ] 非自明なアーティファクトごとに少なくとも1回のフレッシュコンテキストレビューを実施
- [ ] レビュアーには ARTIFACT + CONTRACT のみ渡した（CLAIM や推論は渡していない）
- [ ] レビュアーのプロンプトが敵対的だった
- [ ] 指摘を優先順で分類した
- [ ] 停止条件を満たした
- [ ] インタラクティブモードではクロスモデルを明示的に提案した
