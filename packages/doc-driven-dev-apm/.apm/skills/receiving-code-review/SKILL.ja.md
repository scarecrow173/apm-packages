# コードレビュー受領（Receiving Code Review）

## 概要

コードレビューには技術的評価が必要であり、感情的なパフォーマンスではない。

**核心原則:** 実装前に検証する。仮定前に確認する。社交的快適さより技術的正確性。

## レスポンスパターン

```
フィードバック受領時:

1. READ: 反応せず全フィードバックを読む
2. UNDERSTAND: 要件を自分の言葉で言い換える（または質問する）
3. VERIFY: コードベースの現実に照らして確認
4. EVALUATE: このコードベースにとって技術的に妥当か？
5. RESPOND: 技術的な確認または理由ある反論
6. IMPLEMENT: 一つずつ、各々テスト
```

## 禁止レスポンス

- 「おっしゃる通りです！」（形式的）
- 「素晴らしい指摘！」（形式的）
- 「今すぐ実装します」（検証前）

## 不明確なフィードバックの処理

不明確な項目がある場合: 何も実装せず停止し、不明確な項目について明確化を求める。

## 反論すべき場合

- 提案が既存機能を壊す
- レビュアーが完全なコンテキストを欠いている
- YAGNI に違反（未使用機能）
- このスタックに技術的に不正確
- レガシー/互換性の理由がある
- ユーザーのアーキテクチャ判断と矛盾

**反論方法:**
- 技術的根拠を使う（防御的にならない）
- 具体的な質問をする
- 動作するテスト/コードを参照
- アーキテクチャ的ならユーザーを巻き込む

## 正しいフィードバックの認め方

```
✅ 「修正しました。[変更内容の簡潔な説明]」
✅ 「良い指摘 — [具体的問題]。[場所]で修正。」
✅ [修正してコードで示す]

❌ 形式的な感謝表現
```

## 実装順序

複数項目のフィードバック:
1. まず不明確なものを全て明確化
2. 実装順: ブロッキング問題 → シンプルな修正 → 複雑な修正
3. 各修正を個別にテスト
4. 回帰がないことを確認

## 結論

**外部フィードバック = 従うべき命令ではなく、評価すべき提案。**

検証する。質問する。それから実装する。
