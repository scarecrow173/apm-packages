# ソース駆動開発（Source-Driven Development）

## 概要

フレームワーク固有のコード判断はすべて公式ドキュメントで裏付けなければならない。記憶から実装するのではなく、検証し、引用し、ソースをユーザーに示す。トレーニングデータは古くなり、API は非推奨になり、ベストプラクティスは変化する。このスキルにより、すべてのパターンが権威あるソースに遡れるコードをユーザーに提供する。

## 使用タイミング

- 特定フレームワークの現在のベストプラクティスに従ったコードが必要な場合
- プロジェクト横断でコピーされるボイラープレートやスターターコードを構築する場合
- ユーザーが明示的にドキュメント検証済み、「正しい」実装を求めた場合
- フレームワーク推奨のアプローチが重要な機能の実装時（フォーム、ルーティング、データ取得、状態管理、認証）
- フレームワーク固有パターンを使ったコードのレビュー・改善時
- フレームワーク固有コードを記憶から書こうとしている時

**使用しない場合:**

- 特定バージョンに依存しない正確性の場合（変数名変更、タイポ修正、ファイル移動）
- 全バージョン共通のロジック（ループ、条件分岐、データ構造）
- ユーザーが速度を検証より優先した場合

## プロセス

```
DETECT ──→ FETCH ──→ IMPLEMENT ──→ CITE
  │          │           │            │
  ▼          ▼           ▼            ▼
 スタック   関連ドキュ  ドキュメント   ソースを
 検出      メント取得   パターン準拠   提示
```

### Step 1: スタックとバージョンを検出する

プロジェクトの依存ファイルを読み、正確なバージョンを特定する。

バージョンが不明確な場合は**ユーザーに確認する**。推測しない。

### Step 2: 公式ドキュメントを取得する

実装する機能の特定ドキュメントページを取得する。ホームページではなく、該当ページを取得する。

**ソース優先度:**

| 優先度 | ソース | 例 |
|--------|--------|---|
| 1 | 公式ドキュメント | react.dev, docs.djangoproject.com |
| 2 | 公式ブログ / changelog | react.dev/blog |
| 3 | Web 標準リファレンス | MDN, web.dev |
| 4 | ブラウザ/ランタイム互換性 | caniuse.com, node.green |

**権威なし — プライマリソースとして引用しない:**

- Stack Overflow の回答
- ブログ記事やチュートリアル
- AI 生成ドキュメント
- 自身のトレーニングデータ

### Step 3: ドキュメントのパターンに従って実装する

- ドキュメントの API シグネチャを使用する（記憶からではなく）
- ドキュメントが新しい方法を示す場合、新しい方法を使う
- 非推奨パターンは使わない
- ドキュメントにないものは未検証とフラグを立てる

**ドキュメントと既存コードが矛盾する場合:** 矛盾を表面化し、ユーザーに選択肢を提示する。

### Step 4: ソースを引用する

フレームワーク固有のパターンにはすべて引用を付ける。

- フル URL を使用（短縮しない）
- 可能な限りアンカー付きのディープリンクを使用
- 非自明な判断には該当箇所を引用
- ドキュメントが見つからない場合は明示的に未検証と記載

## 検証チェックリスト

- [ ] 依存ファイルからフレームワーク・ライブラリのバージョンを特定した
- [ ] フレームワーク固有パターンについて公式ドキュメントを取得した
- [ ] すべてのソースが公式ドキュメントである
- [ ] コードが現バージョンのドキュメントパターンに従っている
- [ ] 非自明な判断にフル URL のソース引用がある
- [ ] 非推奨 API を使用していない
- [ ] ドキュメントと既存コードの矛盾をユーザーに表面化した
- [ ] 検証できなかったものは明示的に未検証とフラグを立てた
