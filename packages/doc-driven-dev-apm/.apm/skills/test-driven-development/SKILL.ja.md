# テスト駆動開発（Test-Driven Development）

## 概要

テストを先に書く。失敗を確認する。通すための最小限のコードを書く。

**核心原則:** テストの失敗を見ていなければ、そのテストが正しいものをテストしているか分からない。

## 使用タイミング

**常に:** 新機能、バグ修正、リファクタリング、動作変更

**例外（ユーザーに確認）:** 使い捨てプロトタイプ、生成コード、設定ファイル

## 鉄則

```
失敗するテストなしにプロダクションコードを書かない
```

テスト前にコードを書いた？削除する。最初からやり直す。

## Red-Green-Refactor

### RED — 失敗するテストを書く

何が起こるべきかを示す最小限のテストを一つ書く。

- 一つの振る舞い
- 明確な名前
- 実コード（モックは不可避な場合のみ）

### RED の検証 — 失敗を確認する

**必須。スキップ不可。**

確認項目:
- テストが失敗する（エラーではなく）
- 失敗メッセージが期待通り
- 機能がないために失敗している（タイポではなく）

### GREEN — 最小限のコード

テストを通す最もシンプルなコードを書く。機能追加もリファクタも「改善」もしない。

### GREEN の検証 — 通過を確認する

**必須。** テストが通り、他のテストも通り、出力がクリーンであること。

### REFACTOR — クリーンアップ

GREEN の後のみ: 重複除去、名前改善、ヘルパー抽出。テストをグリーンに保つ。振る舞いを追加しない。

## 順序が重要な理由

テストを後から書くと即座に通る。即座に通ることは何も証明しない。

TDD は実用的である:
- コミット前にバグを発見（デバッグより速い）
- 回帰を防止（テストが即座に破損を検知）
- 振る舞いを文書化（テストはコードの使い方を示す）
- リファクタリングを可能に（自由に変更、テストが破損を検知）

## レッドフラグ — 中止してやり直し

- テスト前のコード
- 実装後のテスト
- テストが即座に通る
- テスト失敗理由を説明できない
- 「後で」追加されるテスト
- 「今回だけ」の合理化

**すべて意味するもの: コードを削除。TDD でやり直し。**

## 検証チェックリスト

- [ ] 全ての新しい関数/メソッドにテストがある
- [ ] 実装前に各テストの失敗を確認した
- [ ] 各テストが期待した理由で失敗した
- [ ] 各テストを通す最小限のコードを書いた
- [ ] 全テストが通る
- [ ] 出力がクリーン（エラー・警告なし）
- [ ] テストが実コードを使用（モックは不可避な場合のみ）
- [ ] エッジケースとエラーをカバー

## デバッグとの統合

バグ発見？再現する失敗テストを書く。TDD サイクルに従う。テストが修正を証明し回帰を防止する。

テストなしにバグを修正しない。
