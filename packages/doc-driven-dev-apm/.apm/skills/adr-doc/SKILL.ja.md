# ADR Documentation Skill

コーディングエージェント向けの実行可能な仕様として Architecture Decision
Record を書くときにこの skill を使います。

人間は判断を承認し、コーディングエージェントはそれを実装します。そのため ADR
には、エージェントが追加質問なしに動けるだけの文脈、制約、対象範囲、実装方針、
検証基準を含める必要があります。

## 基本方針

- ADR を単なる履歴ではなく、実装ガイドとして書く。
- 制約は可能な限り明示的かつ測定可能にする。
- non-goals を書き、エージェントが範囲を広げないようにする。
- 分かる場合は、判断を具体的なファイル、ディレクトリ、インターフェイス、
  依存関係、パターンに結び付ける。
- テスト、コマンド、レビュー手順、観測可能な振る舞いで確認できる検証基準を含める。
- 判断履歴を保全する。新しいテンプレートに合わせるためだけに古い根拠を書き換えない。

## ADR を書くタイミング

次のような判断では ADR を書く、または提案します。

- システムの構築、連携、デプロイ、運用、拡張方法を変える。
- 依存関係、アーキテクチャパターン、API 規約、データモデル、
  インフラ選択、横断的なルールを導入する。
- コードを書いた後では戻しにくい。
- 将来このコードベースで作業する人間やエージェントに影響する。
- 実質的な代替案があり、そのトレードオフを実装後も残す必要がある。
- 既存の accepted ADR と矛盾する、置き換える、または詳細化する。

既存パターン内の定常的な実装判断、小さなバグ修正、誤字修正、
formatter や linter で管理される好み、既存 ADR がすでに扱っている判断では、
新しい ADR を作りません。

将来のコーディングエージェントが安全にコードを変更するために
「なぜこの選択をしたのか」を知る必要があるなら、ADR に残します。

## エージェントの能動的トリガー

コーディング中に次の状況に出会ったら、作業を続ける前に ADR を提案します。

- プロジェクトにまだ存在しない依存関係を追加しようとしている。
- 他のコードが従うべき新しいパターンを作ろうとしている。
- 複数の現実的な選択肢があり、トレードオフが自明ではない。
- accepted ADR と矛盾する実装をしようとしている。
- 局所的な実装説明ではなく、アーキテクチャ上の「なぜ」を長いコメントに書こうとしている。

提案するときは、遭遇した判断、なぜ重要か、どの実装作業を支配するかを伝えます。

## 作成ワークフロー

### Phase 0: 先に調査する

ユーザーに質問したり ADR を書いたりする前に、次を行います。

1. `references/adr-conventions.ja.md` のディレクトリ規約に従って既存 ADR を探す。
2. 関連する accepted ADR を読み、新しい判断を制約する、関連する、
   または置き換えられる判断を確認する。
3. 判断に関係する技術スタックと依存関係マニフェストを確認する。
4. 関連コードを読み、ADR が支配するファイル、インターフェイス、テスト、
   既存パターンを探す。
5. コード、ドキュメント、PR メモに既存 ADR 参照がないか確認する。

この文脈を意図確認に持ち込みます。リポジトリ内に具体的な証拠があるのに、
抽象的な要求だけから ADR を書かないでください。

### Phase 1: 意図を確認する

質問は一度に 1 つずつ行います。codebase scan で分かっていることは質問しません。

次を確認します。

- 判断タイトル。短い動詞句にする。
- なぜ今この判断が必要なのか。
- 技術スタック、コードベース、期限、運用、コンプライアンス、チーム作業から来る制約。
- 成功基準と失敗シグナル。
- 検討した現実的な選択肢と、それぞれのトレードオフ。
- 現時点での有力案と理由。
- decision-makers、consulted experts、informed stakeholders。
- non-goals と明示的に対象外にする範囲。
- 影響するファイル、ディレクトリ、インターフェイス、依存関係、設定、テスト、パターン。
- 実装が判断に従っていることを証明する検証手順。

ドラフト前に、確認した意図を要約し、ユーザーに修正または承認してもらいます。
実装計画、制約、検証基準を推測しなければ埋められない場合は、ADR を書く前に
追加で確認します。

### Phase 2: ADR を書く

1. `references/adr-conventions.ja.md` に従って ADR ディレクトリとファイル名を選ぶ。
2. `references/template-variants.ja.md` に従ってテンプレートを選ぶ。
3. 判断が単純、局所的、誤解されにくい場合を除き、`full` テンプレートを優先する。
4. 確認済みの意図から、具体的な内容で ADR を埋める。
5. 実装計画には、影響するパス、従うパターン、避けるパターン、依存関係、
   設定、移行作業、互換性対応を必要に応じて書く。
6. 検証基準はチェックボックスで書く。各項目はエージェントが検証できる内容にする。
7. `relations` フロントマターで、置き換え、置き換えられた、関連、詳細化の関係を接続する。

推奨スクリプト:

```bash
node scripts/new_adr.ts --title "Adopt MADR"
node scripts/new_adr.ts --title "Use PostgreSQL" --template full --dir docs/decisions
```

### Phase 3: エージェント対応レビュー

作成した ADR は `references/review-checklist.ja.md` でレビューします。

レビュー結果は短くまとめます。

- エージェントが実装できるだけ十分な点。
- エージェントが追加質問を必要とする不足点。
- 確定するか、不足点を直すか、意図確認に戻るか。

ADR が、何を変更し、何を維持し、何を避け、どのように完了確認するかを
コーディングエージェントに伝えられない場合は、ユーザーが明示的に不足を
受け入れない限り、確定前に修正します。

## 既存 ADR を参照する

アーキテクチャ、データフロー、API、インフラ、依存関係、横断的規約に触れる作業では、
実装前にこの skill を使って既存 ADR を参照します。

1. ADR ディレクトリと索引を見つける。
2. 関連する accepted ADR を、実装計画と検証基準まで含めて読む。
3. 対象コードを変更するときは、有効な判断に従う。
4. コードと ADR が矛盾している場合は、黙って片方を選ばず、人間に報告する。
5. 有効な判断を置き換える必要がある場合は、新しい ADR を作り、`relations` で接続する。

便利なコマンド:

```bash
node scripts/list_adrs.ts --dir docs/adr
node scripts/audit_adr.ts --dir docs/adr
node scripts/review_adr.ts --dir docs/adr
node scripts/check_code_links.ts --dir docs/adr
node scripts/update_index.ts --dir docs/adr --write
node scripts/relate_adr.ts --from 0002-new.md --to 0001-old.md --relation supersedes --write
node scripts/migrate_report.ts --dir docs/adr
```

## コードと ADR のリンク

ADR の実装計画には、その判断が支配するコードを記載します。ADR に直接従うコードには、
判断の主要な入口で ADR を指す軽量コメントを追加してもよいです。

コード参照は少なく保ちます。目的は将来のエージェントが判断を発見できることであり、
すべての行に注釈を増やすことではありません。

## 保守ルール

- ADR 規約の正本として `references/adr-conventions.ja.md` を扱う。
- ツール固有の安全な挙動とレビュー観点は `references/adr-maintenance.ja.md` を参照する。
- この skill では MADR 4.0.0 を ADR 専用の基準として扱う。
- 将来追加される ADR 以外の document skill には MADR ルールを適用しない。
- 既存 ADR があるリポジトリで `--write` を使う前に、明示的なユーザー確認を優先する。
- status 変更、置き換え判断、移行レポートでは、履歴を保全し、古い根拠を置き換えずに文脈を追記する。
