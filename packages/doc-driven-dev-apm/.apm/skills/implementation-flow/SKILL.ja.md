# Implementation Flow

<SUBAGENT-STOP>
特定のタスクを実行するためにサブエージェントとしてディスパッチされた場合、
このメタスキルをスキップし、ディスパッチ指示に従うこと。
</SUBAGENT-STOP>

タスク単位で適切なワークフロースキルを発見・ルーティングしてコード実装を
オーケストレーションする。これは**実装フェーズのディスパッチャー**であり、
「どのスキルを」「どの順序で」呼び出すかを決定し、検証を経てから次に進む。

これは**メタスキル**であり、コードを直接生成しない。代わりにスキルの選択、
順序付け、そして実装を上流文書に接続する検証ループを管理する。

## 利用タイミング

- 承認済み `task-doc` エントリのコード変更を実行するとき。
- 複数のワークフロースキルを協調させて計画を実装するとき。
- `doc-driven-dev-flow` から Phase 5 の委譲先として呼び出されるとき。
- ドキュメントが既に存在し、実装ガイダンスだけが必要なとき（スタンドアロン利用）。
- 実装作業を開始するとき — 正しくルーティングするためにまずこのスキルを呼ぶ。

## ルール

**コードを書く前に、下記の Skill Discovery を通してルーティングすること。**
ワークフロースキルが適用される場合、必ず使うこと。これは任意ではない。
合理化してスキップすることは許されない。

---

## Skill Discovery

実装タスクが到着したとき、この決定木でルーティングする:

```text
タスクが実装に到着
    │
    ├── バグ修正 / テスト失敗？ ─────────→ systematic-debugging（最初に）
    │       次に → test-driven-development（回帰防止）
    │
    ├── 複数の独立タスク/障害？ ──────────→ dispatching-parallel-agents
    │       （ファンアウト後、各サブタスクがこの木に再入）
    │
    ├── サブエージェントに委譲？ ─────────→ subagent-driven-development
    │       （サブエージェントは明示的なスキル指示を受領）
    │
    └── 直接コード実装？ ────────────────→ LAYER STACK（該当する全てを適用）:
            │
            ├─ [常時] test-driven-development
            │     全変更に RED → GREEN → REFACTOR
            │
            ├─ [複数ファイル変更時] incremental-implementation
            │     薄い垂直スライス、各スライスを検証してから拡張
            │
            ├─ [フレームワーク/ライブラリ時] source-driven-development
            │     実装前に公式ドキュメントで検証
            │
            ├─ [非自明な判断時] doubt-driven-development
            │     アプローチをコミットする前に敵対的レビュー
            │
            └─ [タスク完了後] requesting-code-review
                  フィードバック受領時は receiving-code-review
```

**原則:** スキルは排他的ではなくレイヤーとして重ねる。単一タスクで通常
2〜4 スキルが同時に活性化する（例: `incremental-implementation` +
`test-driven-development` + `source-driven-development`）。

---

## スキル優先順位

複数スキルが該当する場合、この順序で適用する:

| 優先度 | カテゴリ | スキル | 理由 |
| ------ | -------- | ------ | ---- |
| 1 | Process | `systematic-debugging` | 修正の前に診断が必要 |
| 2 | Process | `test-driven-development` | テストが正しさを定義する |
| 3 | Implementation | `incremental-implementation` | 作業を構造化する |
| 3-alt | Implementation | `subagent-driven-development`, `dispatching-parallel-agents` | 代替実行モード |
| 4 | Verification | `source-driven-development` | 権威ある情報源で検証 |
| 5 | Verification | `doubt-driven-development` | 判断に挑戦する |
| 6 | Review | `requesting-code-review` | 実装後 |
| 7 | Review | `receiving-code-review` | フィードバックへの対応 |

Process スキルはアプローチを決定する。Implementation スキルは実行を構造化する。
Verification スキルは正しさを検証する。Review スキルはループを閉じる。

---

## スキルタイプ

| スキル | タイプ | 意味 |
| ------ | ------ | ---- |
| `test-driven-development` | **Rigid** | 厳密に従う。RED フェーズを絶対にスキップしない。 |
| `systematic-debugging` | **Rigid** | 4 フェーズプロセスを厳密に従う。推測しない。 |
| `incremental-implementation` | **Rigid** | 5 ルールを厳密に従う。ビッグバン変更禁止。 |
| `requesting-code-review` | **Rigid** | 提出前にチェックリストを厳密に従う。 |
| `receiving-code-review` | **Rigid** | レスポンスパターンを厳密に従う。 |
| `source-driven-development` | **Flexible** | DETECT→FETCH→IMPLEMENT→CITE を文脈に合わせる。 |
| `doubt-driven-development` | **Flexible** | リスクに応じて doubt サイクルの深さを調整する。 |
| `subagent-driven-development` | **Flexible** | タスク形状に合わせてディスパッチパターンを調整する。 |
| `dispatching-parallel-agents` | **Flexible** | 利用可能リソースに合わせて並列度を調整する。 |

**Rigid スキル:** プロセスをステップバイステップで従う。ステップを飛ばさない。
規律を緩めない。これらは痛い教訓から得たプラクティスを体現する。

**Flexible スキル:** 原則を適用し、具体的なステップは文脈に合わせる。
文字通りの遵守より精神が重要。

## 行動規範

実装全体を通じて適用する。交渉の余地はない。

### 1. 上流文書と照合する

実装前に、task-doc の要件と ADR の制約が理解と一致することを確認する。
一致しない場合は STOP し明確化する — 黙って再解釈してはならない。

### 2. 仮定を表面化する

非自明なことを実装する前に、仮定を明示する:

```text
このタスクの前提:
1. [task-doc から読み取ったスコープの前提]
2. [ADR からの制約の前提]
3. [design-doc からのインタフェースの前提]
→ 今訂正がなければ、この前提で進めます。
```

### 3. タスク境界を尊重する

task-doc が指定した範囲のみ実装する。以下は禁止:

- 副作用として隣接コードを「整理」する
- タスクスコープにない機能を追加する
- タスクが要求する以上のリファクタ
- 明示的承認なしに未使用コードを削除する

タスク境界内での外科的精度が仕事。

### 4. 混乱を能動的に管理する

コードが spec と矛盾、design が ADR と矛盾、実装がギャップを明らかにした場合:

1. **STOP。** 推測で進めない。
2. 具体的な矛盾を明示する。
3. 上流文書のオーナーにフィードバックする。
4. ループバックを理由 1 行で記録する。
5. 解決を待ってから継続する。

### 5. 簡潔さを強制する

実装を完了する前に:

- より少ない行数でできないか？
- この抽象化は複雑さに見合うか？
- design-doc の意図に合致し、超過していないか？

100 行で十分なら 1000 行書かない。

### 6. 検証し、思い込まない

タスクは検証を通過するまで完了ではない。「良さそう」は十分ではない。
エビデンスが必要: テスト合格、ビルド出力、またはランタイムデータ。

## プロセス

各タスク単位について:

1. **タスク選択** — `task-doc` から次の実行可能タスクを選ぶ（依存順序を尊重）。
2. **ルーティング** — Skill Discovery 木を辿り、該当する全スキルを特定する。
3. **宣言** — どのスキルを適用するか、なぜかを述べる。
4. **実行** — 選択スキルを優先度順に適用し、各スキルのプロセスに従う。
5. **検証** — タスクが定義された検証条件を満たすことを確認する。
6. **フィードバック** — 新たな制約が発見された場合、`adr-doc` / `design-doc` を更新する。
7. **レビュー** — `requesting-code-review` を呼び出し、フィードバックは `receiving-code-review` で対応。
8. **反復** — 全タスク完了までステップ 1 に戻る。

## 推奨組み合わせ

| シナリオ | スキル | 備考 |
| -------- | ------ | ---- |
| 標準実装 | `incremental-implementation` + `test-driven-development` + `requesting-code-review` | 大半のタスクのデフォルト |
| フレームワーク多用 | + `source-driven-development` | 公式ドキュメント検証を追加 |
| 高リスク / 未知領域 | + `doubt-driven-development` + `source-driven-development` | 最大検証 |
| 自律マルチタスク | `subagent-driven-development` | 内部で TDD とレビューを含む |
| 複数障害デバッグ | `systematic-debugging` + `dispatching-parallel-agents` | 並行根本原因追跡 |
| バグ修正 | `systematic-debugging` → `test-driven-development` | 診断してからガード |

## Hard Gates

<HARD-GATE>
すべてのタスクは検証条件を通過してから完了とする。
現タスクにテスト失敗や未解決の検証条件がある場合、次タスクに進んではならない。
</HARD-GATE>

<HARD-GATE>
実装中に spec や design の誤りまたは不足が判明した場合、
実装を中断し適切な上流文書へフィードバックしてから継続すること。
ループバックは理由を 1 行記録する。
</HARD-GATE>

<HARD-GATE>
Skill Discovery ルーティングをスキップしてはならない。スキルが該当するなら
必ず使うこと。「これは簡単だからスキップしてよい」が最も多い失敗パターン。
</HARD-GATE>

---

## Red Flags

これらの思考が浮かんだら STOP — スキルスキップを合理化している:

| 思考 | 現実 |
| ---- | ---- |
| 「単純な変更だから TDD は不要」 | TDD は交渉不可。まず失敗するテストを書く。 |
| 「コードが動いてからテストを書こう」 | それは TDD ではない。RED が先。常に。 |
| 「このライブラリは十分知っている」 | 公式ドキュメントで確認する（`source-driven-development`）。 |
| 「この判断は自明だ」 | 代替案があるなら `doubt-driven-development` を使う。 |
| 「ついでに隣のコードを整理しよう」 | `task-doc` のスコープ内に留まる。整理は新タスクを起票。 |
| 「この小さな修正にレビューは不要」 | 全タスクに `requesting-code-review`。例外なし。 |
| 「全部まとめて直せる」 | 1 スライスずつ（`incremental-implementation`）。 |
| 「このスキルのプロセスは大げさだ」 | Rigid スキルはショートカットがバグを生むから存在する。使う。 |
| 「まずこれだけやらせて」 | 何かをする前に Skill Discovery でルーティング。 |
| 「いい感じに進んでいる」 | スキルルーティングなしの無規律な行動は時間の無駄。 |

## 失敗パターン

このスキルが防ぐ一般的な実装の失敗:

1. **TDD スキップ** — 失敗するテストなしにコードを書き、後からテストを追加。
2. **ビッグバン実装** — インクリメンタルスライスの代わりに 10 ファイルを一度に変更。
3. **思い込み駆動コーディング** — ドキュメント検証の代わりに記憶に基づいて実装。
4. **スコープクリープ** — 実装中にタスク境界外のコードを「改善」。
5. **当て推量デバッグ** — 体系的な根本原因追跡の代わりにコードをランダムに変更。
6. **レビュースキップ** — コードレビュー提出なしにタスクを完了マーク。
7. **暗黙の再解釈** — フィードバックなしに task-doc と異なるものを実装。
8. **過剰設計** — タスクが要求しない抽象化やインフラを構築。
9. **ループバック信号の無視** — spec/design のギャップが明らかでも実装を続行。
10. **エビデンスなき確信** — テスト合格や検証出力なしに「動いている」。

## エントリ条件

- 検証条件が定義されたタスク単位（`task-doc` または同等）が存在すること。
- `doc-driven-dev-flow` から呼び出される場合、Phase 4 タスクが承認済みであること。

## 完了条件

- 全タスク単位が実装済みである。
- 各タスクが定義された検証条件を通過している。
- 実装中に発見された新制約が上流文書に反映されている。
- コードレビューが完了している（`requesting-code-review` / `receiving-code-review` 経由）。

## ループバックルール

- タスクが spec の不足を明らかにした場合 → spec/design 担当にフィードバック; そのタスクを一時停止。
- タスクスコープ内で解決できないテスト失敗 → `systematic-debugging` を呼び出す。
- 複数の独立タスクがブロックされた場合 → `dispatching-parallel-agents` を検討。
- 実装が ADR 制約と矛盾した場合 → ADR を更新するかアプローチを変更。
- ループバック時は理由を 1 行記録する。

---

## 指示の優先順位

1. **ユーザーの明示的な指示**（AGENTS.md、直接の要求）— 最優先。
2. **このスキルおよび呼び出されたワークフロースキル** — デフォルト動作を上書き。
3. **デフォルトシステムプロンプト** — 最低優先。

ユーザーが「このタスクは TDD をスキップ」と言えば、ユーザーに従う。
ユーザーが主導権を持つ。ただし上書き指示がない場合、スキルは必須。
