# implementation-profile Schema

This document defines the structure and validation rules for
`.sdp/implementation-flow-default/implementation-flow-profile.json`, generated
for `implementation-flow` through `skill-discovery-protocol`.

## File Location

- **Path:** `.sdp/implementation-flow-default/implementation-flow-profile.json`
- **Generated by:** `skill-discovery-protocol` with adapter path `.apm/skills/implementation-flow/assets/adapters/implementation-adapter.yaml`
- **Updated by:** re-invoking `skill-discovery-protocol` when skills or inference data change

## Top-Level Fields

```json
{
  "adapter_id": "implementation-flow-default",
  "flow_profile": "implementation-flow-profile.json",
  "generated_at": "YYYY-MM-DDTHH:mm:ss.sssZ",
  "runtime_guidance": {},
  "flow_stack": {
    "slots": []
  },
  "resolved_invocations": []
}
```

| Field | Type | Required | Description |
| ----- | ---- | -------- | ----------- |
| adapter_id | string | Yes | Must be `implementation-flow-default` for the distributed implementation adapter |
| flow_profile | string | Yes | Output filename for the generated profile JSON |
| generated_at | string | Yes | ISO timestamp when the profile was generated |
| runtime_guidance | object | Yes | Queryable guidance such as execution policies and runtime hints |
| flow_stack | object | Yes | Slot assignments that define the default implementation skill stack |
| resolved_invocations | array | Yes | Fully resolved skill-routing decisions derived from classification and overrides |

## Sections

### 1. Available Skills

A table listing all discovered skills with metadata.

| Column | Required | Description |
| ------ | -------- | ----------- |
| Name | Yes | Skill identifier (matches directory/file name) |
| Category | Yes | One of the defined categories |
| Source | Yes | Where the skill was discovered |
| Activation | Yes | One of: `always-on`, `conditional`, `excluded` |
| Execution | Yes | One of: `rigid`, `flexible` |
| Condition | No | When activation is `conditional`, describes trigger |

### 2. Category Assignments

Groups skills by category. Each category has a description and the list of skills assigned to it.

**Valid categories:**

| Category | Purpose | Example Skills |
| -------- | ------- | -------------- |
| Process | Determine approach to the task | debugging, planning, task-breakdown |
| Build | Structure and execute implementation | incremental-implementation, TDD, frontend-engineering |
| Verify | Validate correctness and quality | source-driven-development, doubt-driven-development |
| Review | Post-implementation quality gates | code-review, security-audit |
| Domain | Language/framework/platform-specific guidance | TypeScript conventions, React patterns, API design |
| Tooling | Tool-specific workflows | git, CI/CD, browser-devtools |
| Meta | Skills that orchestrate other skills | implementation-flow, doc-driven-dev-flow |

### 3. Default Stack

Defines the base skill combination applied to standard implementation tasks. This is the "starting point" that gets augmented based on task characteristics.

Structure:

```markdown
## Default Stack

| Priority | Category | Skill | Rationale |
| -------- | -------- | ----- | --------- |
| 1 | Process | <skill> | <why always applied> |
| 2 | Build | <skill> | <why always applied> |
| ... | ... | ... | ... |
```

### 4. Override Rules

Optional section for repository-specific routing overrides.

Structure:

```markdown
## Override Rules

| Condition | Action | Reason |
| --------- | ------ | ------ |
| <when this is true> | <add/remove/replace skill> | <why> |
```

## Validation Rules

1. Every skill in "Available Skills" must have a valid category from the defined set.
2. Every skill in `flow_stack.slots` must exist in "Available Skills".
3. `activation` must be one of: `always-on`, `conditional`, `excluded`.
4. `conditional` skills must have a non-empty `Condition` field.
5. At least one skill must be `always-on` in the `Build` category.
6. The `Meta` category should not appear in `flow_stack.slots` (meta skills orchestrate, not execute).

## Staleness Detection

A profile is considered stale when:

1. A new skill directory exists that is not listed in "Available Skills".
2. A listed skill's source directory no longer exists.
3. `last_validated` is older than 30 days.
4. The repository's technology stack has visibly changed (new language, framework, etc.).

When stale, `implementation-flow` proposes an update rather than silently regenerating.
