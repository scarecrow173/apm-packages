# スキル発見プロトコル

`implementation-profile.md` が存在しないか、陳腐化が検出された場合にこのプロトコルを実行します。出力はリポジトリルートに生成された `implementation-profile.md` です。

## ステップ 1: すべてのスキルソースをスキャン

次の場所を順番にスキャンします。各場所について、スキル名、説明（フロントマターまたは最初の見出しから）、およびソースパスを収集します。

| 優先度 | ソース | 探すもの |
| ------ | ------ | ------ |
| 1 | `.apm/skills/` | `SKILL.md` を含むディレクトリ |
| 2 | `.agents/skills/` | `SKILL.md` を含むディレクトリ |
| 3 | `.github/skills/` | スキルマークダウンファイル（GitHub Copilot） |
| 3 | `.github/agents/` | エージェントペルソナファイル `*.agent.md` |
| 3 | `.cursor/rules/` | ルールマークダウンファイル（Cursor） |
| 3 | `.claude/commands/` | コマンドファイル（Claude Code） |
| 3 | `.gemini/skills/` | スキルファイル（Gemini CLI） |
| 3 | `.gemini/commands/` | コマンド TOML ファイル（Gemini CLI） |
| 3 | `.opencode/skills/` | スキルファイル（OpenCode） |
| 4 | システムスキル | エージェントコンテキスト/命令にリストされたスキル |
| 5 | `apm_modules/` | スキルを持つインストール済みパッケージ |
| 6 | `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` | ルート命令ファイルで参照されているスキル |
| 6 | `.cursorrules`、`.windsurfrules` | インラインスキルコンテンツ |
| 6 | `.github/copilot-instructions.md` | 参照されているスキル |

## ステップ 2: 発見されたスキルを分類

説明と目的に基づいて、各スキルを正確に 1 つのカテゴリに割り当てます:

| カテゴリ | 割り当てルール |
| -------- | ------------ |
| Process | スキルが*アプローチを決定* (デバッグ、計画、タスク分割) |
| Build | スキルが*実行を構造化* (TDD、インクリメンタル、フロントエンド、API 設計) |
| Verify | スキルが*正確性を検証* (ドキュメント検証、対抗的レビュー、セキュリティ) |
| Review | スキルが*実装後のゲート* (コードレビュー、パフォーマンス監査) を提供 |
| Domain | スキルが*言語/フレームワーク/プラットフォーム固有* (TypeScript、React、Python) |
| Tooling | スキルが*ツール使用を支配* (git、CI/CD、ブラウザー devtools) |
| Meta | スキルが*他のスキルをオーケストレーション* (このスキル、doc-driven-dev-flow) |

## ステップ 3: アクティベーションモードを決定

各スキルにアクティベーションモードを割り当てます:

| モード | 意味 | 基準 |
| ------ | ---- | ---- |
| always-on | すべてのタスクに適用 | コア方法論スキル (例: TDD、インクリメンタル) |
| conditional | タスクが条件に一致する場合に適用 | タスク特性によってトリガー |
| excluded | このリポジトリでは使用されない | リポジトリのテクノロジー/ドメインに無関係 |

## ステップ 4: 実行モードを分類（Rigid vs Flexible）

各スキルについて、そのプロセスにどの程度厳密に従う必要があるかを決定します:

| モード | 定義 | 適用方法 | 例 |
| ------ | ---- | -------- | -- |
| Rigid | 厳密なステップバイステップのプロセスを指定 | 正確に従う; ステップを飛ばしたり順序を変えない | TDD (RED-GREEN-REFACTOR)、systematic-debugging (5 ステップ診断) |
| Flexible | 手順より原則を指定 | 精神を適用; 文脈に合わせる | source-driven-development (ドキュメントに対して検証)、code-review (多軸評価) |

**分類基準:**

- スキルが番号付きステップ、明示的なフェーズ、または必須のシーケンスを定義している場合 → **Rigid**
- スキルが厳密な順序なしに目標、原則、またはチェックリストを定義している場合 → **Flexible**

エージェントがスキルを文字通りに従うべきか適応すべきかわかるよう、実行モードをプロファイルに記録します。

## ステップ 5: デフォルトスタックを定義

すべてのタスクの基盤となる `always-on` スキルを選択します。次の順序で:

1. **Process** スキルが最初（アプローチを決定）
2. **Build** スキルが 2 番目（実行を構造化）
3. **Verify** スキルが 3 番目（検証）
4. **Review** スキルが最後（ループを閉じる）

ドメインとツーリングスキルは常に `conditional` です — タスク特性によってアクティベーション。

## ステップ 6: `implementation-profile.md` を生成

プロフィールをリポジトリルートに書き込みます。`assets/templates/implementation-profile-template.md`
のテンプレートを使用し、`references/implementation-profile-schema.md` に対して検証します。生成されたプロフィールをユーザーに提示してから続行します。

## ステップ 7: 陳腐化チェック（プロフィールが存在する場合）

`implementation-profile.md` が既に存在する場合、検証します:

1. リストされたすべてのスキルソースが引き続き存在する。
2. リストされていない新しいスキルディレクトリが表示されていない。
3. `last_validated` の日付が 30 日以内である。
